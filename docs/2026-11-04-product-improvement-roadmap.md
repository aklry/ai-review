# AI 面试训练助手优化方案与实施路线

> 日期：2026-11-04  
> 状态：M1 功能已实现，2026-11-05 全量真实模型自动验收 125/125 通过，独立人工校准待完成；M2–M5 待实施  
> 目标用户：3–5 年经验的前端与 AI 应用开发者  
> 实施记录：[M1 规范题与逐项评分](./superpowers/plans/2026-11-04-standard-question-rubrics.md)

## 1. 产品目标

让用户通过多次训练，在相近难度的新问题中，独立给出更准确、更有依据、更清楚的回答。

围绕这一目标，将现有“简历 → JD → 文字模拟 → 单场报告”推进为可持续的训练闭环：

```text
确认个人经历与求职目标
  → 基于规范题和评分标准进行诊断
  → 定位具体知识点或表达缺口
  → 一键开始专项练习
  → 根据反馈重答
  → 使用同难度变式题复测
  → 更新能力记录与下一次训练计划
```

产品延续现有面试准备与模拟训练定位。优先把前端和 AI 应用场景做深，通用岗位扩张、企业招聘和自动投递不进入近期迭代。

## 2. 当前基线与差距

以下基于当前仓库实现，不把原方案中的规划能力视为已实现。

| 能力       | 当前实现                                                | 下一步差距                                       |
| ---------- | ------------------------------------------------------- | ------------------------------------------------ |
| 候选人资料 | PDF/DOCX 文本解析、手动输入、结构化事实提取、STAR 故事  | 缺少便捷的事实确认、修订与跨岗位复用入口         |
| 岗位分析   | 基于简历和 JD 的四维分析、证据引用、缺失事实提示        | 缺少围绕同一求职目标的多轮准备管理               |
| 出题       | 按能力配额一次性生成主问题                              | 缺少规范题实体、稳定题目版本及动态选题           |
| 题库       | `questionInventory` 定义 120 题的数量蓝图               | 尚未形成对应的规范题目、逐题评分标准和样例       |
| 追问       | 每道主问题最多追问一次                                  | 缺少澄清、验证、加深、切换等显式决策             |
| 评分       | 1–5 分、四维聚合、引用校验、未测评维度为 `null`         | 缺少逐题评分锚点、结论与证据绑定、评分稳定性评测 |
| 报告       | 优势、缺口、七天计划、历史逐题复盘                      | 计划不能直接启动专项练习，缺少重答和复测         |
| 交互       | 文字回答、即时反馈、恢复进行中的会话                    | 缺少语音、完整模拟模式、工程实战题               |
| Agent 基础 | 五个 Agent、LangGraph、checkpoint、超时与降级、用量记录 | 需要补充可检索记忆、受约束决策和效果指标         |

| 用户体系   | `local-user` 本地 MVP                                   | 对外多人使用前需要可信身份与资源归属检查         |

P0 表示下一阶段优先交付；P1 表示依赖基础能力逐步交付；“发布前必需”是多人使用的前置条件，不受功能优先级影响。

| 阶段       | 优先级 | 交付主题                         | 主要依赖                     | 完成标志                               |
| ---------- | ------ | -------------------------------- | ---------------------------- | -------------------------------------- |
| M1         | P0     | 规范题、逐题评分标准与模型评测   | 现有文字训练链路             | 能解释为什么得分，并验证基本评分质量   |
| M2         | P0     | 薄弱项专项练习、重答与变式复测   | M1 的知识点、题目与评分版本  | 从报告进入练习，完成后更新能力记录     |
| M3         | P1     | 动态追问、练习/模拟模式          | M1；个性化选题使用 M2 记录   | 根据回答推进，同时保持覆盖和时长边界   |
| M4         | P1     | 语音训练与录音复盘               | 稳定的会话及媒体存储生命周期 | 录音、纠错、评分和回听完整可用         |
| M5         | P1     | 前端与 AI 工程案例               | M1 的题目类型扩展            | 能评价代码与排障思路，不只评价概念描述 |
| 持续迭代   | P1     | 资料复用、求职目标、工作台与体验 | M2 先提供最小关联模型        | 用户能快速继续训练并理解下一步         |
| 多人发布前 | 必需   | 身份、资源隔离、删除与成本监控   | 部署模式和身份方案           | 不同用户数据隔离，运行问题可追踪       |

实施顺序为 M1 → M2 → M3，再推进 M4/M5。工作台的轻量调整可以随 M2 交付。采用里程碑验收，不把此路线视为固定日期承诺。

## 5. M1：规范题与可信评分

### 5.1 题库范围

首批建设 24 道规范题，每个能力维度 6 道，优先覆盖典型 L1/L2/L3 场景。这个数量用于建立可人工复核的小型基线，原有 120 题蓝图保留为后续扩充目标。

题库存量分布与一场面试的抽题比例分开管理。标准八题训练先保持当前 1/2/2/3 的维度配额，以及 10/20/30/40 的总分权重，避免同时修改多个评分变量。

每道规范题至少包含：

| 字段                                    | 用途                             |
| --------------------------------------- | -------------------------------- |
| `id`、`version`                         | 稳定题目身份与版本               |
| `competency`、`skillIds`                | 现有四维归属及更细的知识点       |
| `difficulty`、`rounds`、`frameworkTags` | 难度、轮次、Vue/React 等适用条件 |
| `prompt`、`constraints`                 | 标准题干与必要约束               |
| `expectedSignals`、`commonMistakes`     | 预期证据、常见误区及不同有效解法 |
| `rubric`、`rubricVersion`               | 1–5 分的评分锚点和必要条件       |
| `followUpRules`                         | 何时澄清、验证或增加约束         |
| `sampleAnswers`                         | 用于内部评测的不同质量回答       |

样例答案属于评测或讲解材料，不进入候选人事实库，也不在完整模拟作答前展示。

首版采用仓库内版本化内容文件，不先开发题库管理后台。建议位置为 `packages/agent-core/src/question-bank/`；跨端需要的 Zod 契约放在 `packages/contracts`。

### 5.2 出题规则

1. 应用根据轮次、技术栈、难度、覆盖配额和可用题库选择题目。
2. InterviewerAgent 可以使用已确认经历调整题目表述，但不能改变考察目标、必要约束和评分标准。
3. 会话持久化实际题干、标准题 ID、题目版本、评分标准版本与必要快照，防止题库更新改变历史语义。
4. 选择不到适用题目时返回明确的不足信息；可提供标记为探索练习的生成题，不能冒充已有规范题。
5. 暂时保持现有一次追问限制，动态追问在 M3 实施。

### 5.3 评分规则

CoachAgent 输出“评分项 → 判断 → 回答证据/缺失项 → 分值依据”，应用校验结构与确定性规则，再执行四维聚合。

- 引用存在性和引用能否支持结论是两种不同检查。前者由代码校验，后者需要明确评分标准、评测样例和人工抽检共同验证。
- 已满足或错误的判断应关联具体回答片段；“未提及验证方法”等缺失项单独记录，不能为了满足引用要求编造原文。
- 明确区分知识错误、未说明细节、表达不清，分别给出下一步建议。
- 接受满足条件的不同方案，不以参考答案措辞一致作为得分依据。
- 简短且正确的回答可以获得高分；不能仅靠篇幅、术语数量或 STAR 格式决定技术得分。
- 现有未测评维度继续为 `null`，覆盖不足时不生成完整总分。
- 主问题计分、追问作为补充证据的现有语义在 M1 保持不变。

示例：“介绍一次前端性能优化”需要分别判断定位依据、方案取舍、验证方法和结果。只说“用了懒加载”不能被视为已经证明定位准确或效果可靠。

### 5.4 历史兼容

- 新增评分版本，例如 `rubric-v3`；最终名称在实现时统一定义。
- 保留 `legacy-v1` 与 `evidence-v2` 报告，不自动重算。
- 旧记录新增字段允许为空或具有明确默认值。
- 复盘页面显示评分版本；不同版本的总分不直接计算进步幅度。
- 模型输出必须通过校验后写入持久化反馈；失败不能留下貌似有效的评分。

### 5.5 效果评测与验收

建议首批为每道题准备好、中、弱三类回答，共 72 个基础样例，并增加简短正确、冗长错误、无关回答、英文表达、缺少量化结果和诱导修改评分规则等边界样例。

样例标签需人工复核。开发集用于调整提示词，另留独立验收样本，避免只记住固定答案。

| 验收项     | 检查方式                                                                                             |
| ---------- | ---------------------------------------------------------------------------------------------------- |
| 题库完整性 | 题目 ID 唯一，所有题目有知识点、版本、评分锚点和样例                                                 |
| 选题约束   | 满足轮次/技术栈要求和标准场的四维覆盖；同场不重复抽取同一规范题                                      |
| 规则正确性 | 非法分数、无来源引用、模型篡改版本等确定性用例必须通过                                               |
| 历史兼容   | 旧报告仍可读取，新报告快照可追溯，未测评语义不变                                                     |
| 评分区分   | 统计好、中、弱回答排序；建议初始目标为强弱区分正确率至少 90%                                         |
| 评分稳定性 | 固定题目、评分版本、模型配置，对代表样例重复评分并报告分布；建议至少 90% 的重复组最大分差不超过 1 分 |
| 人工复核   | 抽检扣分依据、不同有效解法及示范建议；记录分歧样例而非只报平均分                                     |

以上百分比是拟定验收目标，不是当前测量结果。真实模型评测保持显式开启、使用虚构资料、限制调用预算并保存失败记录；不能用 mock 测试通过替代模型效果验收。

## 6. M2：专项练习、重答与复测

### 6.1 用户流程

```text
报告发现“缓存失效策略说明不足”
  → 点击“开始专项练习”
  → 回答同知识点的递进题
  → 查看具体反馈并重答
  → 使用未见过的相近难度题复测
  → 显示本次改善的证据与仍需练习的内容
```

七天计划由纯文本升级为可执行任务。每项任务包含来源缺口、关联知识点、预计时长、状态和启动入口。

### 6.2 建议数据关系

以下为拟新增概念，实际 Prisma 字段在实现时定稿：

| 实体              | 主要职责                                               |
| ----------------- | ------------------------------------------------------ |
| `PreparationGoal` | 公司、岗位、JD、目标轮次和准备时间，关联资料及多场训练 |
| `TrainingTask`    | 来源报告/反馈、知识点、练习类型、状态和完成条件        |
| `PracticeAttempt` | 关联练习会话、题目、先前尝试和反馈，保留每次回答       |
| `SkillProgress`   | 用户及求职目标下的知识点状态、最近证据和复测时间       |

首版重答优先创建关联练习会话或新的尝试记录，保留原场回答及评分；不要直接覆盖现有每题唯一的 `InterviewAnswer`。

任务创建和启动采用幂等键，避免刷新或重复点击创建多份任务/会话。生成推荐不依赖新增通用 Agent，可先按题目标签、反馈缺口和规则完成。

### 6.3 比较与验收

- 区分“看过反馈后的同题重答”与“未见过的变式复测”，前者不直接证明独立掌握。
- 比较相同知识点、相近难度、兼容评分标准的结果，样本不足时显示证据不足。
- 保留原始回答、重答与复测证据，用户能看懂具体改善了什么。
- 历史报告没有知识点或评分标准版本时仍可浏览，但不自动加入严格趋势计算。
- 从报告到练习、刷新恢复、重复启动、提前退出、完成回写均有明确状态。
- 用户完成练习后，任务状态和工作台内容一致更新。

## 7. M3：动态面试官与训练模式

### 7.1 显式推进决策

保留整场能力覆盖计划，逐轮根据回答选择动作：

| 回答情况                    | 动作                           |
| --------------------------- | ------------------------------ |
| 职责或描述含糊              | `clarify`：要求具体说明        |
| 结论缺少依据                | `verify`：追问数据、验证或反例 |
| 基础掌握充分                | `deepen`：增加约束或讨论取舍   |
| 已覆盖考察目标              | `next`：进入下一知识点         |
| 到达时长/追问上限或用户结束 | `finish`：保存状态并结束       |

应用负责允许动作、追问深度、时间预算和能力覆盖，Agent 只在允许集合中给出建议。支持用户澄清、跳题、暂停和结束，并持久化状态变化。

多层追问统一关联根主问题，新增深度与顺序信息；调整当前依赖直接父题的推进逻辑。历史单层追问需兼容，新增事件写入继续复用租约、版本检查和事务机制。

### 7.2 练习模式与模拟模式

- 练习模式：逐题反馈、查看解释、重答和专项训练。
- 模拟模式：作答期间不展示评分和示范答案，结束后统一复盘。

新增独立的反馈策略字段，不改变现有 `preparation/simulation/authorized-assist` 模式枚举的含义。模拟模式的反馈展示限制应在服务端响应投影执行，不能只在前端隐藏。

验收重点：新问题与回答相关；不会无限追问；不会因追问漏掉必要维度；暂停/重试不跳题；模拟模式不会提前返回应延后展示的反馈。

## 8. M4：语音训练与回听

先交付用户主动控制的逐题录音，再考虑自然轮流对话和打断。

1. 开始前检查麦克风并提供问题朗读。
2. 用户主动开始/结束录音，界面明确展示状态。
3. 转写后允许检查和纠错，确认文本再送入内容评分。
4. 保存原始转写、用户确认文本及必要的时间对应信息。
5. 复盘支持逐题回听，语音失败时可切回文字继续。

内容分和表达指标分别展示。回答时长、停顿、重复表达等作为训练反馈，不用口音或语速直接推断技术能力。用户编辑后的文本若不能准确映射音频，不生成虚假的片段定位。

媒体文件使用私有存储、限时访问、明确保留周期和删除规则。验收覆盖权限拒绝、无声录音、转写错误、网络中断、播放失败和恢复训练；自然对话阶段再额外测量首段转写延迟及轮流发言体验。

## 9. M5：前端与 AI 工程实战

首批采用代码片段、日志和静态案例，先验证题目与反馈价值。

| 类型     | 示例                                     | 评价依据                           |
| -------- | ---------------------------------------- | ---------------------------------- |
| 前端代码 | 修复搜索请求乱序覆盖、异步组件状态错误   | 正确性、边界处理和解释             |
| 性能排查 | 根据性能数据与加载瀑布提出优化方案       | 诊断依据、验证方法、方案取舍       |
| 系统设计 | 在吞吐、成本与一致性约束下设计接口和缓存 | 假设、容量估算、失败处理           |
| AI 应用  | 基于检索结果解释 RAG 评估与改进          | 评测设计、证据质量、成本和延迟取舍 |

只有接入隔离执行环境并真实执行后，才展示“测试通过”；未执行时明确表示静态评审。代码执行后续单独建设，包含资源限制、超时和网络边界。

## 10. 个人资料、求职目标与工作台

### 10.1 三类可复用信息

| 信息       | 来源与使用方式                                  |
| ---------- | ----------------------------------------------- |
| 候选人事实 | 简历和用户确认的故事，保留来源、版本与确认状态  |
| 求职目标   | 用户提供的岗位、公司、JD 和轮次，限定训练上下文 |
| 能力记录   | 训练中的回答、评分和复测，关联题目与时间        |

模型生成的改写建议不自动成为个人事实。跨会话读取优先按用户、目标、知识点和来源记录做结构化查询；资料规模扩大后再评估是否需要向量检索。

STAR 故事改为引导补充：发现缺少个人贡献、方案取舍或结果依据时追问，再由用户确认保存。修订简历不应丢失属于同一用户的训练历史，但需要保留训练时的资料快照。

### 10.2 工作台和等待体验

- 首页优先显示继续训练、今日专项练习、当前求职目标和最近复测结果。
- 提供示例资料或快速练习入口，允许用户先体验再补充完整资料。
- 服务地址、API 检查和实现名称移至设置/诊断区；正常训练界面显示用户能理解的状态。
- 长任务提供真实阶段进度和明确失败恢复，不展示虚构百分比。
- 逐步输出可读内容时，最终评分和引用仍须完整校验后再发布。

## 11. 多人发布与运行质量

本节是从本地 MVP 走向多人使用的必要工程范围。

### 11.1 身份与数据生命周期

- 用可信登录身份替换硬编码 `local-user`，不接受客户端自行指定数据所有者。
- 在简历、岗位、故事、训练、报告及新增练习任务的所有读写入口检查归属。
- 数据删除覆盖数据库记录、对象存储、checkpoint 和派生记录；失败可重试且结果可追踪。
- 生产日志避免记录简历正文、完整回答和密钥，按操作 ID 关联排障信息。

### 11.2 成本与性能

- 记录分析、出题、评分、报告各阶段耗时、失败与降级，并在足够样本下统计 P50/P95。
- 区分逻辑调用与修复/备用模型等实际尝试，避免低估成本。
- 模型价格使用可配置且有生效时间的版本记录，不长期依赖名称匹配和固定价格常量。
- 对重复提交、取消、失败重试和任务恢复检查是否产生重复调用或重复写入。
- 当前 API 内任务租约与恢复机制继续使用；出现实际排队、资源隔离或媒体处理需求后再启用 worker，不为占位入口提前引入双重调度。

### 11.3 产品效果指标

优先观察首次完成训练比例、报告后启动专项练习比例、复测完成比例，以及同知识点同难度的表现变化。使用时长和模型调用次数不能单独证明学习效果；获得 offer 的结果也不能直接归因为产品。

## 13. 验证策略与完成定义

实现阶段针对行为变化添加必要测试，重点覆盖选题约束、评分规则、版本兼容、会话幂等和恢复；不增加只重复实现细节的测试。

- 单元与契约测试：题库、评分和输入输出规则。
- 数据库集成测试：增量迁移、旧记录、新快照、事务及并发推进。
- 桌面测试和界面检查：评分依据、状态切换、错误与空状态。
- 真实模型评测：显式启用，记录样例、模型、版本、耗时和结果。
- 完成相应检查后执行仓库要求的格式、lint、类型检查、测试与构建。

每个里程碑的交付记录应包含实际完成范围、测试结果、模型评测结果与剩余限制。没有执行的检查注明未执行，不把方案中的验收目标记为已通过。
