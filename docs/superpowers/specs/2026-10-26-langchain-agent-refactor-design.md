# LangChain 分步 Agent 重构设计提案

日期：2026-10-26

状态：用户已于 2026-10-26 回复“继续”；2026-10-28 已实施并验证，详见对应实施计划的最新验收记录。

## 1. 目标与范围

将现有文字面试流程重构成职责明确、输入输出可校验、可单独测试的五个 Agent，使用 LangChainJS 封装模型交互，使用 LangGraph 显式编排步骤和分支。

首轮继续使用 NestJS、DeepSeek、Prisma/PostgreSQL、现有 Vue/Electron UI 和 HTTP API。上传、文件解析、权限、事务、计分和题目游标由确定性代码执行。用户提交回答是流程输入，不能由 Agent 代替。

本次重构目标是改善边界、流程可靠性和可追踪性，不宣称框架本身会提高评分准确率，也不把全部业务步骤改成额外的模型调用。

## 2. 现状依据

- `apps/api/src/interview/interview.service.ts` 集中承担岗位分析、题目生成、Coach、报告、下一题选择和用量记录。
- `apps/api/src/deepseek/deepseek.provider.ts` 已实现结构化结果解析、主备模型、总超时预算和 token 用量返回。
- `packages/agent-core/src/index.ts` 已包含四类提示词、模型 JSON 兼容处理和计分规则。
- `CandidateProfile.structuredResume` 已存在，但当前简历流程主要写入提取文本。
- `apps/worker/src/index.ts` 尚无真正的 BullMQ 消费者；API 内启动后台 Promise 不具备任务调度和重启恢复保障。

本轮前序核查已用实际源码与内存数据库桩复现：

1. 第一题追问答完后会跳到第三题。
2. 同一题重复提交只有一个 answer 记录，但题目游标会递增两次。
3. 无反馈时现有聚合函数可得出四维各 3/5、总分 60/100。
4. 分析页卸载停止轮询，重新进入不会自动恢复轮询。

这些问题必须有明确的业务修复和回归用例，不能只靠替换模型 SDK。

## 3. 方案比较

| 方案                                      | 做法                                                  | 取舍                                                           |
| ----------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------- |
| 仅拆 LangChain Runnable                   | 五个独立步骤，由 NestJS 手写调用顺序                  | 改动较小，但分支、暂停恢复和运行状态仍需业务层另行实现         |
| LangChain + 固定 LangGraph 工作流（推荐） | 五个 Agent 作为智能节点，代码控制有向边、校验、持久化 | 与当前确定的面试流程贴合，便于检查每一步并限制循环             |
| 自主 Supervisor 多 Agent                  | 由另一个模型决定调用哪个 Agent、执行几轮              | 增加调用、延迟与不可预测性；当前流程已有明确顺序，首轮没有必要 |

采用第二种。每个 Agent 独立持有任务提示词、输入输出契约、模型参数和测试。单次提取/评估可使用结构化模型调用；只有确实需要工具或自主决策的步骤才引入工具调用循环。

## 4. 五个 Agent 的职责

| Agent            | 输入                                           | 输出                                           | 约束                                                   |
| ---------------- | ---------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------ |
| ProfileAgent     | 提取的简历文本、用户确认的故事                 | 结构化经历、技能、项目、带来源的事实及缺失信息 | 不补造事实；按文本与故事版本复用结果                   |
| JobAgent         | JD、岗位设置、已确认档案                       | 现有 JobAnalysis：四维能力分析、考点、待补证据 | 四个维度各出现一次；引用必须来自所提供的资料           |
| InterviewerAgent | 能力分析、题目计划、当前回答上下文、允许的动作 | 初始题目集合，或一条限定范围的澄清/追问        | 不写数据库；不能任意修改主问题游标或无限追问           |
| CoachAgent       | 当前题目、用户回答、相关事实与评分标准         | 当前题反馈、证据、缺口和是否需要追问的建议     | 不选择最终业务状态；结果必须关联当前题和能力维度       |
| ReportAgent      | 已完成题目、校验后的反馈、确定性评分结果       | 总结、优势、薄弱项和七天训练计划               | 不自行覆盖分数，不为未测评维度编分；数据不足须明确说明 |

初始题目规划先收敛在 InterviewerAgent 内，七天计划先收敛在 ReportAgent 内。后续若它们需要独立数据、工具或评估体系，再拆独立 PlanningAgent，避免首轮徒增调用。

## 5. 流程编排

准备流程：

```text
文件校验与文本提取
  -> ProfileAgent（有有效缓存则复用）
  -> JobAgent
  -> 输出与证据校验
  -> 保存岗位分析
  -> 等待用户开始训练
```

创建会话：

```text
读取已完成分析
  -> InterviewerAgent 生成题目
  -> 代码检查数量、四维覆盖和核心题规则
  -> 事务保存计划、会话和题目
  -> 等待用户回答
```

每题流程：

```text
验证会话状态、题目和请求幂等性
  -> 读取当前题所需的事实
  -> CoachAgent
  -> 校验反馈、证据与维度
  -> 固定路由：有限追问 / 下一道主问题 / 等待结束
       -> 如需追问，调用 InterviewerAgent
  -> 事务保存本轮结果及下一状态
  -> 返回反馈与下一题
```

结束流程：

```text
验证结束条件、读取已持久化反馈
  -> 代码聚合计分并标明未测评维度
  -> ReportAgent
  -> 校验报告及七天计划
  -> 事务保存报告与完成状态
```

这些是多个按用户动作触发的流程，不是在上传后一次性执行到报告。等待回答时不占用一个持续运行的 HTTP 请求或 worker。

## 6. 状态与持久化边界

- Prisma 业务表保存档案、岗位、题目、回答、评分、报告和权威会话状态。
- 显式区分 `baseQuestionIndex`、`activeQuestionId`、`parentQuestionId` 与追问次数。追问不递增主问题游标，主问题完成后才推进。
- LangGraph checkpoint 保存工作流恢复所需的执行状态，并通过业务标识与操作版本关联。部署使用 PostgreSQL checkpointer；内存实现仅用于测试。
- Graph checkpoint 与 Prisma 事务不是天然的同一个事务。业务副作用必须幂等；恢复时先核对已提交业务结果，不能盲目重复写入或再次计分。
- 同一会话的推进串行化，通过数据库条件更新/锁和状态版本阻止并发冲突。
- 同一题、相同回答的重试返回已保存结果，不重复调用模型或推进状态；修改已提交回答需要显式规则，首轮拒绝静默覆盖。
- 首轮每个主问题最多一次追问。追问结果作为补充证据，不新增一个独立计分题；主问题评分修订必须显式保留关联，不能把追问简单加入维度平均。
- 最后一题完成后返回明确的等待结束状态，前端清空当前输入并禁止继续提交该题。
- 前端回到分析页时按持久化状态恢复轮询；加载会话时以服务端状态恢复当前题。
- Checkpoint 提供恢复信息，不会自动唤醒失去执行进程的后台任务。岗位分析需要真实持久任务与 worker 重试，或应用启动后的恢复调度，才能满足重启恢复验收。

## 7. 模型接入与输出契约

先保留现有 provider 的超时、主备模型、usage 和错误语义，提供统一 AgentModelGateway。将 LangChain 模型适配放在该边界内部，逐步接入 `ChatDeepSeek`，防止业务节点直接依赖供应商 SDK。

- 官方提供 `@langchain/deepseek` 集成，但实际配置模型的结构化输出、扩展参数与缓存 token 元数据仍需适配测试验证。
- 保留总时间预算；关闭或显式计入 SDK 内部重试，避免 SDK、Agent、Graph 和 worker 层层重试放大调用。
- 每个 Agent 有独立 Zod 输入与输出校验。输出字段存在不等于事实成立，证据引用还要与原始资料核对。
- 禁止缺失评分时补成 3/5、模型失败时合成一份看似成功的报告。缺少必要字段返回明确的失败或有限重试。
- 限定传给每个 Agent 的上下文，不给所有步骤重复注入全部简历与历史对话。
- 每次调用记录真实 taskType、模型、prompt/schema 版本、耗时、token 和降级情况。外部 tracing 默认不上传原始简历和回答。

## 8. API 与代码组织

既有 HTTP 路由和成功/失败信封继续保留。Controller 继续做请求边界校验，InterviewService 变成调用工作流并读取业务结果的应用服务。

建议组织：

```text
packages/agent-core/src/
  agents/             # 五个 Agent 的契约、提示词与独立实现
  workflows/          # 准备、创建会话、答题、报告图和纯路由规则
  scoring/            # 确定性计分、未测评和追问计分规则
  validation/         # 证据与题目覆盖校验
  ports/              # 模型、业务存储、执行状态接口

apps/api/src/
  agents/             # NestJS 注入、LangChain 模型与 checkpoint 适配
  interview/          # 原有 HTTP 接口和 Prisma 持久化
  resume/             # 文件上传、存储、解析

apps/worker/src/
  consumers/          # 持久岗位分析任务及恢复执行
```

共享包不导入 NestJS、Prisma 或服务端 Secret。数据库与模型配置在服务端注入。

未测评不能继续伪装成整数分数，因此报告契约需要有明确迁移：增加维度测评状态，并让未测评分数可空；更新 contracts、API 和 UI。已有报告不自动重算，可标记为旧计分版本。不能为了“保持 API 兼容”隐藏这一行为变更。

## 9. 建议实施顺序

1. 为追问推进、重复提交、末题收尾和未测评评分建立回归测试；将事务和状态规则从模型调用中分离。
2. 接入 LangChain 模型网关，迁移现有 Job、Interviewer、Coach、Report 四类调用，保持前端入口可用。
3. 增加 ProfileAgent，将结构化档案写入已有 structuredResume，加入缓存失效规则。
4. 以 LangGraph 串联智能节点和确定性节点，接入 PostgreSQL checkpoint 与真实后台任务恢复。
5. 更新前端状态恢复和未测评展示，运行全量测试、类型检查、构建及真实依赖集成验收。

每一步都应产出可运行、可回归验证的增量，避免一次性替换整个文字面试系统。

## 10. 验收标准

- 五个 Agent 可分别替换为 fake model 测试，成功和异常输出均有覆盖。
- 追问后准确返回下一道主问题；重复提交与并发提交不跳题、不重复写入或重复计分。
- 已结束会话拒绝继续回答；最后一题完成后 UI 有明确终态。
- 没有回答时不产生虚假的能力分数；未覆盖维度显示未测评；追问不作为额外计分题平均。
- 准备/报告任务中断并恢复后，已经提交的业务副作用不重复执行。
- 服务端重启后持久任务可恢复；分析页切换后重新轮询并展示最终结果。
- SDK 与应用层重试共享预算，失败不会被默认文本和默认分数伪装成成功。
- 历史报告版本可识别；共享契约、客户端与服务端的未测评语义一致。
- 原有测试、lint、typecheck、build 通过；真实 DeepSeek、PostgreSQL、Redis 的集成验收单列结果，不能以 mock 测试替代。

## 11. 暂不扩展

首轮不新增语音、OCR、向量数据库、独立 Safety LLM、自主 Supervisor、企业招聘功能或完整题库内容。鉴权和数据隔离仍是上线前工作，不因本次 Agent 重构而视为完成。
