# MVP 问题评估与修复方案

日期：2026-09-04

## 结论

当前文字面试 MVP 的主链路是：上传简历 -> 粘贴 JD -> 岗位分析 -> 生成题目 -> 逐题回答 -> 训练报告。

以下三项属于 P0，必须修复后才适合继续验证 MVP 效果：

1. 导航切换不能丢失训练流程状态。
2. 相同简历必须通过内容 hash 去重，命中后复用已有档案和 MinIO 对象。
3. 岗位分析必须有总超时预算、结果复用和明确的失败反馈。

LangChainJS 暂不作为 MVP 的必选依赖。当前 Agent 只是多个职责明确的结构化模型调用，现有 `agent-core + DeepSeekProvider + Zod` 已能支撑验证产品效果。等到需要工具调用、并行专家、条件分支、长流程恢复或统一 tracing 时，再在服务端增加 `AgentOrchestrator`，并把 LangChainJS 限制在该边界内。

## 问题一：导航导致内容丢失

### 根因

`TrainingView.vue` 将 `phase`、简历档案、JD、岗位分析、会话、回答和报告全部保存在组件局部 `ref` 中。`App.vue` 使用 `RouterView` 渲染路由组件，切换到其他路由时训练组件会卸载，返回时重新创建，因此局部状态恢复为初始值。

### MVP 修复

新增 Pinia `training` store，保存训练流程所需的业务状态。页面组件只保留 DOM 文件选择器引用和派生计算，提交请求继续由页面触发，数据状态由 store 持有。

本次保留的是应用进程内状态，覆盖路由切换和组件重建；暂不把完整简历正文明文写入 `localStorage`。窗口刷新后的加密恢复属于后续能力。

### 验收标准

- 在工作台和训练配置之间来回切换，已填 JD、STAR 故事和简历档案不丢失。
- 岗位分析完成后切换导航再回来，分析结果仍可见。
- 面试进行中切换导航再回来，当前题目、回答和即时反馈仍可见。
- 点击“重新开始”后，store 中的训练状态全部清空。

## 问题二：相同简历重复上传

### 根因

服务端已经在 `ResumeParserService.inspect()` 中计算 SHA-256，但 `ResumeService` 计算后直接写 MinIO，没有查询已有文档。`ResumeRepository` 也没有按用户和 hash 查找可复用档案的方法。

### MVP 修复

上传处理顺序调整为：

```text
校验文件并计算 sha256
  -> 查询 local-user + sha256 + parsed 文档
  -> 命中：直接返回已有 CandidateProfile 和 ResumeDocument
  -> 未命中：上传 MinIO、解析、保存元数据和 profile
```

`ResumeDocument` 对已解析成功的记录增加 `(userKey, sha256)` 部分唯一约束，避免同一用户对同一份已成功解析的简历产生重复文档记录。失败和解析中的记录保留重试空间。hash 基于文件内容，不受文件名变化影响；内容有任何变化都会生成新的 hash。

本次只复用已成功解析的文档。解析失败的文档仍保留失败记录，便于排查；失败重试和并发上传协调不扩大到本次 MVP 的主改动。

### 验收标准

- 同一用户再次上传完全相同的文件时，`putObject` 不被调用。
- 返回原有 `profileId`、`documentId`、解析文本和元数据。
- 文件改名但内容相同仍能命中。
- 内容改变后不会错误复用旧档案。

## 问题三：点击分析超时无结果

### 根因

桌面端 Axios 和服务端 DeepSeek 单次请求都使用约 45 秒超时。主模型超时后，provider 还会用 fallback 模型再等待一次；因此服务端最坏可能执行两段等待，而客户端在第一段等待结束时已经断开请求。用户看不到最终结果，重复点击还可能导致重复模型调用和重复 Job。

### MVP 修复

1. `DeepSeekProvider` 使用 40 秒总时间预算。主模型优先获得预算，fallback 只能使用剩余时间，不能再额外追加完整超时；桌面端 API 请求使用 50 秒，给服务端响应和数据库写入留出余量。
2. 岗位分析显式限制输出 token，避免分析结果过长拖慢响应。
3. 对完全相同的 `profileId + targetRole + company + jobDescription` 查询已有岗位分析，命中时直接返回，不再次调用模型。
4. 桌面端请求超时留出服务端响应和数据库写入余量，失败时沿用统一错误展示，不保留无限 loading。
5. 主模型失败后最多降级一次；模型输出仍必须通过现有 Zod schema 校验。

本次采用同步请求的最小可靠改造，保证现有 API 兼容。若真实 DeepSeek P95 仍超过总预算，下一步应把岗位分析迁移到 BullMQ 异步任务：创建 task -> worker 执行 -> 前端轮询 task 状态。该异步改造不作为本次前三项修复的必要前置。

### 验收标准

- 主模型失败时最多调用一次 fallback。
- 两次模型调用共享同一总时间预算，不出现 45 秒加 45 秒的串行等待。
- 同一岗位分析重试不会再次调用 DeepSeek，也不会创建重复 Job。
- 模型失败后页面能结束 loading 并显示可重试错误。
- 现有岗位分析、题目生成、Coach 和报告流程的结构化输出契约不变。

## 实施顺序

1. Pinia 训练状态和状态回归测试。
2. 简历 hash 查询、唯一索引、复用逻辑和上传回归测试。
3. DeepSeek 总预算、分析结果复用和超时回归测试。
4. 运行 `pnpm test`、`pnpm typecheck`、`pnpm build`。

## 暂不纳入 MVP

- LangChainJS 多 Agent 编排。
- OCR、语音/ASR、WebSocket 流式事件。
- 完整 120 道题库内容。
- 明文 localStorage 简历缓存。
- 生产级登录、权限、KMS 和跨用户隔离。
- BullMQ 异步岗位分析任务，除非真实模型测试证明同步总预算仍不足。
